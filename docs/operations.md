# Configuration and operations

## Requirements

- Linux for the deployed services (`fcntl`, `/proc`, systemd).
- Python 3.13+ and the root `requirements.txt`; Node.js 22+ and the trading app's npm lockfile.
- For control commands: Docker CLI/daemon access, `dig` (often provided by `dnsutils`), `tar`, and an existing AdGuard container with named volumes.
- An authorized broker market API connection for the collector. This is not a general-purpose public/free quote feed.
- Two separate Telegram bot tokens: one for each bot. One polling owner per token.

The example units assume the repository is at `~/homelab-telegram-bots`. Adjust their `WorkingDirectory` and `ExecStart` if you install elsewhere. Run the root README's dependency installation first. Ensure `node` is available on the systemd user's PATH; if using a version manager, put the absolute Node executable in `EXNESS_TRANSPORT_COMMAND`.

## Private configuration

```bash
mkdir -p ~/.config/homelab-bots
chmod 700 ~/.config/homelab-bots
cp apps/trading-bot/.env.example ~/.config/homelab-bots/trading.env
cp apps/control-bot/.env.example ~/.config/homelab-bots/control.env
chmod 600 ~/.config/homelab-bots/*.env
```

Edit these files for your own machine. Environment variables in the examples are read by systemd; Python does not automatically load `.env`. For an interactive shell, use `set -a; . "$HOME/.config/homelab-bots/trading.env"; set +a` from the trading application directory.

| Setting | Purpose |
| --- | --- |
| `SIGNAL_ENGINE=intraday-shadow` | Process the current strategy into isolated shadow state, with no Telegram object created. |
| `MARKET_DB`, `EXNESS_MARKET_DB` | Must point to the same dedicated `market-exness.db` generated by the collector. |
| `MARKET_SCHEDULE_FILE` | Collector-generated `exness-schedule.json`; required by the launcher. |
| `INTRADAY_SHADOW_DB`, `TRADES_DB` | Separate shadow/live ledgers; never point both to one file. |
| `NEWS_DB` | Calendar cache shared by the news worker and trading bot. |
| `BOT_HEALTH_PORT` | Localhost-only health listener; example uses 18766. |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Trading bot token and destination; unnecessary for the offline demo/shadow mode. |
| `TELEGRAM_ADMIN_CHAT_ID` | Only chat authorized by the control bot; use a private admin chat. |
| `ADGUARD_*` | Docker container, DNS address and named volumes for the control bot. |
| `CONTROL_STATE_DIR`, `CONTROL_BACKUP_DIR` | Optional absolute paths for private control state and backup archives. |

The collector reads three private files from `EXNESS_CREDENTIAL_DIR`:

- `connection.json`: an object with `accountId` and `gatewayUrl` supplied by your authorized broker connection.
- `api-key.txt`: the broker API key.
- `private-key.txt`: matching Ed25519 key material (PKCS#8 PEM, or the 128-character seed/public-key hex format supported by the signer).

Keep this directory outside the repository with mode 700 and its files mode 600. Account IDs, keys and gateway configuration are deliberately absent from the package.

## Start shadow processing

Copy the four example units to `~/.config/systemd/user/`, then reload:

```bash
mkdir -p ~/.config/systemd/user
cp deploy/systemd/*.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user start homelab-market.service
journalctl --user -u homelab-market.service -n 30 --no-pager
```

Wait for the collector to create and populate `apps/trading-bot/state/market-exness.db` and `exness-schedule.json`. The engine needs warmup history and current quotes; the presence of a file alone does not establish readiness.

The market service uses `RestartPreventExitStatus=78`, matching the running source service. A blocked authentication, subscription or schedule error requires operator correction and an explicit service start rather than an endless restart loop. Inspect `INVALID_SCHEDULE` status before restarting; do not bypass calendar validation.

```bash
systemctl --user start homelab-trading.service
curl --fail http://127.0.0.1:18766/health
```

The health JSON must be inspected: HTTP 200 and `alive=true` do not imply `ready=true`. If calendar commands are needed, start `homelab-news.service` after reviewing the provider availability. Optional FRED data requires `FRED_API_KEY`.

Enable services at user-session startup only after validating configuration. For unattended services after logout/reboot, configure systemd user lingering according to your host policy.

## Live signals

The supplied release has unverified parity and research limits. Live mode requires an explicit operator decision. It publishes Telegram signals, not brokerage orders.

To configure an isolated live instance, stop its shadow service, use separate live state, set `SIGNAL_ENGINE=intraday-live`, `DRY_RUN=false`, token/chat configuration, and `INTRADAY_DEPLOY_CONFIG_HASH` to the exact current value printed from the trading directory:

```bash
../../.venv/bin/python -c "from intraday_live import CONFIG_HASH; print(CONFIG_HASH)"
```

Do not set parity flags to true merely to enable this mode; these are separate claims. Existing populated state may require the guarded migration helpers. Do not start this copy against an existing live token, database or `/tmp/xauusd-bot.lock` owner. The legacy release's fixed live lock intentionally limits it to one live instance per host.

## Control bot

Configure its independent token/admin chat and actual AdGuard names. Run `python bot.py --self-test` from `apps/control-bot` before starting `homelab-control.service`.

Available commands: `/status`, `/services`, `/adguard`, `/backup_adguard`, `/restart_adguard`, `/reboot`, `/confirm`, `/cancel`. The bot account needs permission to operate Docker. Reboot needs a narrowly scoped sudo rule for the exact `systemctl reboot` command; no rule is installed by this repository. Restart/reboot still require a matching confirmation within 60 seconds.

Backup archives contain operational data and must stay private. The backup checks archive readability and writes SHA-256 sums, but this is not a complete restore test. The inherited backup uses `alpine:latest`; pin a reviewed image digest for a reproducible operational deployment.

## Recovery and updates

- Read `degraded_reasons`, feed age, frame checkpoints and outbox counts before deciding a process restart fixes an incident.
- Resolve collector authentication/connectivity first when quotes are stale. Do not bypass stale-data gates.
- Take consistent SQLite backups with the SQLite backup API or stop the writer before copying database files. Copying only a live WAL-mode `.db` can miss committed data.
- Reconcile `UNKNOWN` sends before retrying; do not bulk reset them to pending.
- Preserve the newest ledger, checkpoints and outbox. Do not restore an older database just to roll code back.
- Config migrations require a flat engine and drained active outbox. Compare hashes and follow the migration helper preconditions.
- Verify backups by restoring to an isolated location; this package does not claim a production restore drill.
